# Repository Guidance

## Project Overview

This repository contains a Shiny enrollment projection app that is also exported
as a client-side Shinylive application for GitHub Pages. Preserve compatibility
with both conventional Shiny and the browser-hosted webR runtime.

## Architecture

- `app.R` is the application entry point. It includes webR-specific UI
  pre-rendering needed for Safari compatibility.
- `R/model.R` contains parsing, validation, grade-order suggestions, and calls to
  `enrollcast`. Keep domain logic independent of Shiny where practical.
- `R/app.R` contains the UI and session-scoped reactive server.
- `www/` contains app-owned CSS and the webR-only download bridge.
- `tests/testthat/` contains native R and server tests.
- `tests/browser/` contains Playwright tests for the exported application.
- `scripts/` contains the isolated build, lock, test, and export tooling.
- `site/` is generated by `scripts/export-shinylive.R`. Do not hand-edit it or
  store source files there.

## Development Commands

Run commands from the repository root.

```sh
Rscript scripts/test-native.R
Rscript scripts/export-shinylive.R
npm ci
npx playwright install chromium webkit
npm run test:browser
```

For focused browser checks, use `npm run test:browser:desktop`,
`npm run test:browser:mobile`, or `npm run test:browser:webkit`. If the preview
server is already using port 4173, run Playwright with
`PLAYWRIGHT_REUSE_SERVER=1`.

Preview the generated site with `npm run preview`, then open
`http://127.0.0.1:4173/projections-app/`.

## Change Guidelines

- Make the smallest correct change and preserve the continuous one-page workflow.
- Keep visible language direct, plain, and suitable for a public-service tool.
- Maintain keyboard access, visible focus states, semantic HTML, status messages,
  responsive layouts, and useful chart alt text.
- Preserve uploaded grade labels exactly. Grade-order suggestions must remain
  editable and must not invent an order for unknown or ambiguous labels.
- Treat enrollment uploads as sensitive aggregate data. Do not add analytics,
  persistence, external requests, credentials, or third-party assets without an
  explicit requirement and privacy review.
- Do not silently weaken validation, replace missing counts with zero, or bridge
  missing historical years.
- Retain full-precision calculations and CSV exports; round only displayed counts.
- Keep `https://localopen.r-universe.dev` as the canonical `enrollcast` package
  source. Do not add an undocumented repository fallback.

## Shinylive And Safari Constraints

- Do not remove the webR-only static UI pre-rendering in `app.R` without proving
  that the exported app starts in macOS WebKit.
- Keep chart delivery through `renderImage()` unless cross-browser testing proves
  a replacement avoids Safari's webR call-stack failure.
- Keep `www/browser-downloads.js` restricted to webR so native Shiny downloads
  retain their normal behavior.
- Browser tests must exercise the real `site/` export. Do not replace it with a
  mocked UI or add network exceptions to make tests pass.
- Changes to package versions, Shinylive assets, or Wasm artifacts require an
  intentional lock update and review of `scripts/renv.lock`,
  `scripts/wasm-lock.json`, and `scripts/build-config.R`.

## Verification Expectations

- Run `Rscript scripts/test-native.R` for model, server, exporter, or UI changes.
- Re-export with `Rscript scripts/export-shinylive.R` before browser tests when
  application source or assets change.
- Run the relevant Playwright projects for UI or browser-runtime changes. Run the
  full suite when shared behavior, uploads, downloads, reactivity, or rendering
  changes.
- Update tests with behavior changes. Prefer focused model tests for pure logic
  and browser tests for user-visible reactive behavior.
- Run `git diff --check` before committing.

## Generated And Diagnostic Files

- Do not commit generated `site/`, local build libraries, `node_modules/`, or
  Playwright artifacts unless repository policy explicitly changes.
- Browser diagnostics and screenshots under `tests/browser/artifacts/` are test
  outputs. Use them for investigation, not as source files.
- Never manually edit lock files merely to satisfy a failing check; use the
  documented setup and export workflows.
